## LV1

### 50 체육복 — C++ 재구현 (2026-09-09)
- ① 처음 떠올린 방법 : **문제를 먼저 분석**했다. 제한사항의 "여벌을 가져왔는데 도난당한 학생" 줄을 읽고
  코드 쓰기 전에 "교집합을 먼저 걷어내야 한다"와 "그리디 문제다"를 잡아냄
- ② 실제 정답 방법 : 교집합을 양쪽에서 제거 → 낮은 번호 giver 부터 **왼쪽(r-1) 우선**으로 빌려주기
- ③ 사용한 자료구조 : `set<int>` 두 개. 조회·삭제가 `O(log n)` 이고 **순회가 오름차순**이라 정렬이 공짜
- ④ 틀린 이유 : **없음.** 분석 단계를 먼저 거친 첫 문제였고 한 번에 통과했다.

- **배운 것 1 — 그리디의 정당성은 교환 논증으로 증명한다.**
  남은 giver 중 가장 작은 `r` 에 대해, `r-1` 을 도울 수 있는 사람은 `r-2` 와 `r` 뿐인데
  `r` 이 가장 작은 giver 이므로 `r-2` 는 giver 가 아니다 → **`r-1` 은 `r` 말고 대안이 없다.**
  반면 `r+1` 은 `r+2` 가 도울 수도 있다. **대안이 없는 쪽부터 주는 것이 절대 손해가 아니다.**
  실측 반례: 오른쪽 우선으로 바꾸면 `n=4, lost=[1,3], reserve=[2,4]` 가 4 대신 3.
  랜덤 150,026건 중 **1,093건**에서 오른쪽 우선이 손해.

- **배운 것 2 — 그리디는 "순회 순서"가 곧 정확성이다. 그리고 그 순서를 컨테이너가 떠받친다.**
  이 코드에는 `sort` 가 없다. **C++ `set` 이 순회 시 오름차순을 보장**하기 때문이다(46번에서 배운 성질).
  로직을 한 글자도 안 고치고 **`unordered_set` 으로만 바꾸면 랜덤 15만 건 중 1,078건이 틀린다.**
  Python 쪽에서 `sorted(reserve)` 를 명시한 것과 같은 요구다.
  → **그리디를 쓸 때는 항상 "이 순서가 왜 옳은가"에 답할 수 있어야 한다.**

- **배운 것 3 — 그리디는 작은 입력에서 완전탐색과 대조해 검증한다.**
  n 을 2~10 으로 줄이고 모든 빌려주기 조합(왼쪽/오른쪽/안 줌)을 완전탐색한 최적값과 비교했다.
  **225,490건 불일치 0.** "맞는 것 같다"를 "맞다"로 바꾸는 데 5분이면 된다.

- **배운 것 4 — 코드보다 분석이 먼저다.**
  제한사항을 문장 단위로 읽으며 각 줄이 알고리즘의 무엇을 결정하는지 먼저 적었더니 한 번에 통과했다.
  전날 28번은 제한(100만)을 안 읽고 재스캔부터 떠올려 네 번 틀렸다. **같은 사람, 다른 순서, 다른 결과.**

### 28 햄버거 만들기 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : 배열 전체를 훑어 `1,2,3,1` 을 찾고 지우기를 **더 없을 때까지 반복** (재스캔)
- ② 실제 정답 방법 : 스택에 하나씩 쌓고 **쌓을 때마다 맨 위 4개만** 검사. 맞으면 4개 빼기
- ③ 사용한 자료구조 : 스택. 단 별도 컨테이너 없이 **입력 배열을 스택으로 재사용** + 정수 `top` 하나
  → `O(n)` 시간 / 추가 공간 `O(1)`
- ④ 틀린 이유 : **네 번.**
  - `while True` 에 `break` 가 없어 무한 루프. `return` 에 도달 못 함
  - 재스캔 자체가 `O(n²)` → 제한 1,000,000 에서 10¹² 번. **접근이 틀렸다**
  - **검사 순서를 뒤집음.** 재료를 넣기 *전에* 검사하고 `continue` 로 그 재료를 버렸다.
    햄버거는 재료를 하나 더 얹었기 때문에 완성되므로 **얹고 나서** 봐야 한다
  - `a[n-2]==3 && a[n-2]==2` — 같은 인덱스를 두 번 쓰고 `n-4` 를 빠뜨림.
    **항상 거짓**이라 전부 0을 반환. 문법은 정상이라 **컴파일러가 못 잡는다**

- **배운 것 1 — 제한 숫자를 보고 허용 복잡도를 먼저 정한다.**

  | 제한 n | 허용 복잡도 |
  | --- | --- |
  | ~1,000 | `O(n²)` 가능 |
  | ~100,000 | `O(n log n)` 까지 |
  | ~1,000,000 | **`O(n)` 또는 `O(n log n)`** |

  재스캔 실측(앞에 매칭 안 되는 재료를 길게 깐 최악 케이스): 길이 4,000 → 0.0103s,
  8,000 → 0.0416s, 16,000 → 0.1356s, 32,000 → 0.5465s. **n 2배마다 4배 = O(n²)** 가 눈으로 보인다.
  같은 입력에서 스택 방식은 정확히 2배씩만 늘었다.

- **배운 것 2 — 스택을 쓰는 이유는 "새로 생기는 변화가 맨 위에서만 일어나기" 때문이다.**
  새 재료를 얹었을 때 새로 완성될 수 있는 햄버거는 맨 위 4개뿐이다. 그 아래는 하나도 안 변했다.
  그래서 다시 훑을 필요가 없고, 빼내면 그 아래가 새 맨 위가 되어 **"위아래가 맞붙는" 처리도 저절로 된다.**

- **배운 것 3 — `std::stack` 이 아니라 `vector` 를 쓴다.**
  `std::stack` 은 **`top()` 하나만** 보여준다. 이 문제는 위에서 4개를 봐야 하므로 못 쓴다.
  코테에서 스택은 대개 `vector` + `push_back`/`pop_back`/`back()` 이면 충분하고, 안쪽도 들여다볼 수 있다.

- **배운 것 4 — 값으로 받은 매개변수는 버퍼로 재사용할 수 있다.** (72번과 같은 원리)
  `top` 은 1씩 늘고 4씩 줄므로 **"쓰는 자리(top) <= 읽는 자리"** 가 항상 성립한다.
  최악이어도 방금 읽은 자기 자리에 쓸 뿐이고 그 값은 이미 복사돼 있다. 안 읽은 값을 덮을 수 없다.

- **배운 것 5 — `reserve` 는 항상 이득이 아니다.** 실측(100만 개, 전부 햄버거):

  | 구현 | 전부 햄버거 | 랜덤 | 추가 공간 |
  | --- | ---: | ---: | ---: |
  | 별도 vector 스택 | 0.60 ms | 3.83 ms | O(n) |
  | + `reserve` + `resize` | **0.94 ms** | 3.44 ms | O(n) |
  | **입력 재사용 + `top`** | **0.45 ms** | **3.17 ms** | **O(1)** |

  `reserve` 를 넣은 쪽이 **더 느리다.** 이 입력은 스택이 4를 넘지 않는데 400만 바이트를 미리 잡기 때문.
  85번에서는 같은 `reserve` 가 2배 이득이었다. → **기법이 아니라 상황이 성능을 정한다. 재봐야 한다.**

### 23 문자열 나누기 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : 같은 개수·다른 개수 두 카운터를 들고, 같아지면 덩어리 확정 + 카운터 리셋
- ② 실제 정답 방법 : **차이 카운터 하나**를 들고, `cnt == 0` 인 순간에 기준 문자를 새로 정하며 **그때 센다**
- ③ 사용한 자료구조 : 없음. 정수 카운터 하나 + `char` 하나. `O(n)` 시간 / `O(1)` 공간
- ④ 틀린 이유 : **세 번.**
  - 기준 문자 `x` 를 루프 밖에서 한 번만 정함 → 덩어리가 끝나도 기준이 그대로라 이후가 전부 어긋남
  - 기준을 정하는 글자를 `continue` 로 건너뜀 → **기준 문자 자신이 아무 쪽에도 안 세어짐** (`same` 이 끝까지 0)
  - **규칙 3(끝까지 균형이 안 맞으면 그것도 한 덩어리)을 빠뜨림.**
    `"a"` → 0, `"abc"` → 1, 주어진 예제 `"abracadabra"` 도 5. 랜덤 200,000건 중 **143,185건(72%) 오답**

- **배운 것 1 — 두 수의 "같음"은 차이 카운터 하나로 줄어든다.**
  `same == diff` ⟺ `same - diff == 0`. 카운터 하나와 분기 하나가 동시에 사라진다.
  같은 패턴: **괄호 짝 맞추기**(여는 +1 / 닫는 -1), **보이어-무어 다수결**. LV2 `올바른 괄호` 가 이것이다.

- **배운 것 2 — 세는 시점을 "끝"이 아니라 "시작"으로 옮기면 경계 처리가 사라진다.**
  `cnt == 0` = "새 덩어리가 시작된다"이므로 그 자리에서 세면,
  끝까지 균형이 안 맞는 마지막 덩어리도 **이미 세어져 있다** → 루프 뒤 `if` 가 필요 없다.
  이날 72번에서 `if (s.back() == ' ')` 를 없앤 것과 같은 종류. **경계 처리는 잘 짜는 것보다 없애는 게 낫다.**
  실측(200,000자): 카운터 2개 + leftover 0.0040s → 차이 카운터 1개 0.0032s.

- **배운 것 3 — 6월에 이미 알아냈던 것을 다시 헤맸다.**
  `solution2` 주석에 위 두 가지가 그대로 적혀 있었는데, 다시 풀 때 `solution1` 쪽 구조로 시작해 세 번 틀렸다.
  81번에 이어 두 번째다. **문제를 시작하기 전에 그 문제의 기존 기록부터 읽을 것.**

### 72 이상한 문자 만들기 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : `split(" ")` 한 뒤 **단어 인덱스**로 단어 전체를 대/소문자 변환
- ② 실제 정답 방법 : 단어로 나눈 뒤 **그 단어 안의 글자 인덱스**로 글자마다 변환. 이중 루프
- ③ 사용한 자료구조 : `vector<string>` + 수동 join. `O(L)` 시간 / `O(L)` 공간
- ④ 틀린 이유 : **네 번.** 인덱스가 무엇의 인덱스인지 계속 어긋났다.
  - `value == " "` 로 공백을 잡으려 함 → **`split` 은 구분자를 버린다.** 공백은 결과에 들어오지 않는다
  - 단어 인덱스로 단어 전체를 변환 → `'TRYhelloWORLD'`. 문제가 말하는 인덱스는 **단어 안 글자 번호**
  - `" ".join(문자열)` → 리스트가 아니라 문자열을 넘겨 **글자마다** 공백이 들어감 (`'T r Y ...'`)
  - C++ `getline` 이 끝 공백 조각을 버림 → `"abc "` 가 `"AbC"`. 8케이스 중 3개 오답

- **배운 것 1 — Python `split(" ")` 과 C++ `getline(ss, w, ' ')` 은 끝에서 다르다.**
  문자열이 구분자로 끝나면 Python은 마지막 빈 조각을 만들고 **C++은 만들지 않는다.**
  차이는 **항상 정확히 하나**라, 끝이 공백이면 하나를 되돌려 놓으면 된다.
  실측: 이 보정 전 8/9 케이스 중 3개 오답 → 보정 후 랜덤 300,000건 불일치 0.

- **배운 것 2 — 나누지 않는 편이 짧고 빠르다. 최종적으로 이 방식으로 교체했다.**
  글자를 한 번 훑으며 카운터를 들고, 공백을 만나면 카운터를 0으로 리셋하면 끝난다.
  `split`·`join`·빈 조각·이중 루프가 전부 사라지고 **끝 공백 함정도 생기지 않는다.**

  세 구현을 랜덤 300,000건으로 동치 확인 후 실측(C++):

  | 구현 | 200자(제한 최대) | 200,000자 |
  | --- | ---: | ---: |
  | A  split + join + 끝 공백 보정 | 0.829 µs | 990 µs |
  | B  한 번 순회 + 새 문자열 | 0.244 µs | 222 µs |
  | **C  한 번 순회 + 제자리 수정** | **0.192 µs** | **184 µs** |

  C가 A보다 **4.3배 빠르고 본문은 52줄 → 29줄**. → **"문자열을 쪼갠다"가 항상 첫 선택은 아니다.
  상태를 하나 들고 한 번 훑는 쪽을 먼저 검토할 것.**

- **배운 것 4 — 매개변수가 값 복사면 그 복사본을 제자리에서 고쳐 반환하면 된다.**
  `string solution(string s)` 의 `s` 는 이미 호출자 값의 복사본이다. 새 문자열을 또 만들 이유가 없다.
  `for (char& ch : s)` 처럼 **참조**로 받아야 대입이 반영된다. `char ch` 는 사본이라 원본이 안 바뀐다.
  (단, 프로그래머스 스켈레톤 시그니처는 그대로 둔다는 원칙은 유지 — 여기서는 시그니처를 고치지 않았다.)

- **배운 것 3 — 틀린 변수명이 틀린 코드를 유도한다.**
  `for words in arr_s` (실제로는 단어 하나), `for index, word in ...` (실제로는 글자 하나).
  이름이 반대라서 `word.upper()` 로 단어 전체를 바꾸는 실수가 자연스러워 보였다.

### 81 문자열 내 p와 y의 개수 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : p·y가 하나도 없으면 먼저 true를 반환하고, 아니면 개수를 세어 비교
- ② 실제 정답 방법 : 조기 종료를 **빼고**, 한 번의 순회로 둘을 세어 `return p_size == y_size`
- ③ 사용한 자료구조 : 없음. 카운터 두 개. `O(L)` 시간 / `O(1)` 공간
  (Python 풀이는 `lower()`가 새 문자열을 만들어 공간이 `O(L)`, 순회도 3번이었다)
- ④ 틀린 이유 : **조기 종료 한 줄 때문에 랜덤 20만 건 중 37,527건(19%)이 오답.**
  아래 두 줄에서는 대소문자를 둘 다 셌는데, 조기 종료에서는 **소문자만** 봤다.
  `"PP"` → `"p" not in s` 가 참이라 조기 종료로 `True`를 반환. 정답은 `False`.

- **배운 것 — 불필요한 방어 분기가 버그를 만든다.**
  `p_size == y_size` 는 "둘 다 0개"까지 이미 처리한다(`0 == 0`). 그 분기는 **처음부터 필요가 없었고**,
  없었다면 버그도 없었다. **조건 분기는 공짜가 아니다 — 하나 늘 때마다 틀릴 자리가 하나 는다.**
  6월에 같은 파일 주석에 "불필요한 if 분기를 만들지 않는 게 더 안전하고 읽기 쉽다"고 직접 적어놓고
  다시 풀 때 그대로 어겼다. **기록해둔 것을 다시 읽는 것까지가 복습이다.**

- **C++ 문법 — `'p'`(char)와 `"p"`(string)는 다른 타입.**
  `i == "p"` 는 `error: ISO C++ forbids comparison between pointer and integer`.
  `"p"` 는 `{'p','\0'}` 배열의 **주소**이고 `char` 는 숫자값이라 비교가 성립하지 않는다.
  Python에서는 둘이 완전히 같아서 아무거나 써도 됐던 부분이다. 79번에서 적어둔 항목에 또 걸렸다.

### 79 문자열 다루기 기본 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : 루프를 돌며 길이와 숫자 여부를 함께 검사
- ② 실제 정답 방법 : **길이 검사를 루프 밖으로 빼고**, 루프에서는 숫자 여부만 본다 (early return)
- ③ 사용한 자료구조 : 없음. `O(n)` 시간 / `O(1)` 공간
- ④ 틀린 이유 : 정답이긴 했으나 **길이 검사가 루프 안에 있었다.**
  루프와 무관한 조건이라 글자 수만큼 같은 판정을 반복하고, 더 중요하게는
  **빈 문자열이면 루프가 0번 돌아 검사가 아예 실행되지 않고 `True` 가 나온다** (실측 확인).
  이 문제는 제한이 "길이 1 이상"이라 안 터졌다 — **제한이 지켜준 것이지 코드가 옳아서가 아니다.**

- **배운 것 1 — early return.** "조건을 만족하지 않는 것을 앞에서 걸러내고, 통과한 것만 남긴다."
  플래그 변수(`answer = True`)와 `break` 가 사라져 흐름이 한눈에 읽힌다.
  조건이 5~6개 붙는 시뮬레이션 문제에서는 이 모양이 아니면 감당이 안 된다.

- **배운 것 2 — 루프 안에 루프 불변 조건을 두지 않는다.**
  루프를 돌며 값이 변하지 않는 검사는 밖으로 뺀다. 성능보다 **경계 케이스에서 조용히 틀리는 것**이 더 큰 문제다.

- **배운 것 3 — C++에는 문자열 전체를 검사하는 메서드가 없다.**
  Python `s.isdecimal()` 한 줄이 C++에서는 루프가 된다. 그래서 `all(...)` 을 쓰는 Python 풀이가
  C++로 더 자연스럽게 옮겨진다. `isdigit` 대신 `c >= '0' && c <= '9'` 를 쓰면 헤더도 필요 없다.

### 46 두 개 뽑아서 더하기 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : 이중 루프로 모든 쌍의 합을 set에 넣고 정렬해서 반환
- ② 실제 정답 방법 : 같음. C++에서는 `set` 자체가 정렬을 유지하므로 정렬 단계가 사라진다
- ③ 사용한 자료구조 : `set<int>` (중복 제거 + 자동 정렬을 한 번에). `O(n² log n)`, n ≤ 100이라 여유
- ④ 틀린 이유 : **세 번.** 전부 "Python 습관을 C++에 그대로 옮겨서".
  - `for j in range(i, ...)` — 6월 커밋본은 `i+1` 이었는데 다시 쓰면서 `+1` 을 빠뜨림.
    같은 인덱스를 두 번 뽑아 `[2,1,3,4,1]` 에 8(4+4)이 섞임. **문제 조건은 "서로 다른 인덱스"**
  - `tmp_result.add(...)` — C++ `set` 의 삽입은 `insert`. `add` 는 존재하지 않는 이름
  - `set<int>` 를 `vector<int>` 반환 자리에 그대로 돌려줌 — C++은 자동 변환하지 않는다

- **배운 것 — 이름이 같아도 성질이 다르다.**
  Python `set` 은 순서가 없고, **C++ `set` 은 항상 오름차순**이다 (내부가 균형 트리).
  Python `set` 에 성질이 대응하는 건 `unordered_set` 쪽이다.
  이 문제처럼 "중복 제거 + 오름차순"을 동시에 요구하면 C++ `set` 하나로 두 요구가 다 풀린다.

- **뒤의 두 실수는 컴파일러가 100% 잡아줬다.** Python이었다면 `set` 을 그대로 return해도
  에러 없이 실행되고 채점에서 조용히 틀렸을 것이다. 18번의 `[cards1_index] == g` 오타와 정확히 반대 상황.

### 85 같은 숫자는 싫어 — C++ 재구현 (2026-09-08)
- ① 처음 떠올린 방법 : 인접 비교로 `arr[i] != arr[i+1]` 일 때 `arr[i]` 를 남김
- ② 실제 정답 방법 : 같음. 다만 **마지막 원소는 루프가 판정할 수 없어** 루프 밖에서 무조건 추가
- ③ 사용한 자료구조 : `vector` 하나. `O(n)` 시간 / `O(n)` 공간 — **하한이라 더 줄일 수 없다**
- ④ 틀린 이유 : 맨 끝 원소가 빠졌다. 각 원소를 "다음 원소와 비교"해 판정하므로
  마지막 원소는 비교 상대가 없어 구조적으로 건너뛰어진다. 동시에 뒤가 없으니 연속 중복일 수도 없어 **항상 포함**된다.

- **배운 것 1 — "더 최적화할 수 있나"는 감이 아니라 하한과 비교해서 답한다.**
  입력을 전부 읽어야 하면 `O(n)` 이 하한이고, `O(n)` 풀이가 나왔으면 거기서 끝이다.
  이 판단이 서면 이미 최적인 코드를 붙잡고 시간을 태우지 않는다.
  실측: Python 0.0200s / C++ 0.0019s (원소 100만). `itertools.groupby` 는 0.0283s로 **직접 루프보다 느렸다** —
  파이썬에서 "짧은 코드 = 빠른 코드"가 아니다.

- **배운 것 2 — `vector::reserve`.** `push_back` 은 capacity가 차면 더 큰 메모리를 새로 잡고
  기존 원소를 **전부 복사**한다. capacity는 `1→2→4→8→16→32` 로 배씩 늘어나 전체는 분할상환 `O(n)` 이지만,
  상한을 미리 알면 그 복사를 통째로 없앨 수 있다.
  실측(원소 100만): 재할당 6회 → **0회**, 0.0019s → **0.0010s (약 2배)**.
  **`reserve`는 size를 바꾸지 않는다** — `reserve(5)` 후에도 `size()==0` 이라 `v[0]` 접근은 범위 밖이다.
  원소를 실제로 만드는 건 `resize`. 이 둘을 헷갈리면 조용히 망가진다.
  시그니처를 건드리는 `const vector<int>&` 는 이득이 미미하므로 **스켈레톤 그대로 둔다**(기존 원칙 유지).

  **`reserve` 판단 기준 (실측 3건):**

  | 문제 | 잡은 만큼 채우나 | 결과 |
  | --- | --- | --- |
  | 85 같은 숫자는 싫어 | 결과가 입력 길이에 가까움 → **채운다** | **2배 이득** |
  | 58 직사각형 별찍기 | 최종 길이가 정확히 계산됨 → **채운다** | **2.4배 이득** (줄 단위 처리와 합쳐 75배) |
  | 28 햄버거 만들기 | 스택이 4를 안 넘음 → **거의 안 채운다** | **손해** (0.60ms → 0.94ms) |

  → **`reserve` 는 "잡은 만큼 실제로 채울 때"만 이득이다.** 기법이 아니라 상황이 성능을 정한다.

### 18 카드 뭉치 (2026-09-07)
- ① 처음 떠올린 방법 : 각 뭉치의 원소가 `goal`에서 갖는 인덱스가 오름차순이면 통과
- ② 실제 정답 방법 : `goal`을 한 번 훑으며 단어마다 두 뭉치의 **맨 위**와만 비교, 맞으면 그 뭉치 포인터를 전진
- ③ 사용한 자료구조 : 없음. 뭉치마다 정수 포인터 하나씩 (O(len(goal)) 시간, O(1) 공간)
- ④ 틀린 이유 : **네 번 틀림.** 전부 "제한사항을 안 읽어서" 하나로 수렴한다.
  - `goal`에 없는 카드를 건너뛰어도 된다고 가정 → 카드는 버릴 수 없으므로 쓰는 카드는 뭉치의 **prefix**여야 함
    (`cards1=["a","b"], cards2=["c","d"], goal=["b","c"]` 에서 Yes를 내지만 정답은 No)
  - `for index, card in cards1:` 의 `index`가 `goal`이 아니라 `cards1`의 인덱스라 검사가 항상 참
  - `while goal_index > time:` 부등호 반대 → 루프에 한 번도 진입 못 하고 전부 "No". **세 번 지적받고서야 실행해봄**
  - `[cards1_index] == g` 오타. 리스트 vs 문자열 비교라 파이썬은 조용히 False. C++이었으면 컴파일 에러

- **배운 것 — 그리디가 성립한 이유는 제한사항 한 줄이다.**
  "cards1과 cards2에는 서로 다른 단어만 존재합니다" → 한 단어를 낼 수 있는 뭉치가 많아야 하나 → **갈림길이 없다**.
  이 제한을 풀면 (`cards1=["x","a"], cards2=["x","b"], goal=["x","b"]`) 그리디는 No, 정답은 Yes로 **즉시 깨진다**.
  그때는 되돌아가는 백트래킹이 필요하고, `(i, j)`(각 뭉치를 몇 장 썼나)를 캐싱하면 DP가 된다.
  실측(뭉치 12장씩, goal 24단어, 답 No): 백트래킹 7,696,443회 0.47s → `@lru_cache` 한 줄로 **168회 0.000087s**.
  상태 수가 `13 × 13 = 169`뿐이라 그 이상 계산할 이유가 없다.
  → **완전탐색 ⊃ DP(중복 상태 제거) ⊃ 그리디(선택지가 하나뿐일 때)** 는 별개 기술이 아니라 같은 탐색의 축약 단계다.

- C++ : `int cards1_index` 와 `cards1.size()`(unsigned) 직접 비교 → `-Wsign-compare`.
  `int cards1_size = cards1.size();` 로 받아두고 비교 (NOTES 아래 "부호 비교" 항목 그대로).
  `and` 는 C++에서도 합법이지만 관례는 `&&`.

### 34 신고 결과 받기 (2026-08-20, 재풀이)
- ① 처음 떠올린 방법 : 신고 관계를 정방향·역방향 dict 두 개로 저장하고 교집합
- ② 실제 정답 방법 : 역방향 dict 하나만 만들고, 정지 확정 순간 신고자들의 메일 수를 즉시 +1
- ③ 사용한 자료구조 : dict + set (중복 신고를 set이 자동으로 1회 처리)
- ④ 틀린 이유 : 틀리지는 않았으나 dict 2개는 불필요. 방향을 뒤집으니 메모리 절반, 속도 2배 (0.0805s → 0.0442s)

### 53 완주하지 못한 선수 (2026-08-21)
- ① 처음 떠올린 방법 : `set(participant) ^ set(completion)`
- ② 실제 정답 방법 : 이름별 인원을 dict로 세고, `completion`을 돌면서 하나씩 깎기
- ③ 사용한 자료구조 : dict (`.get(name, 0) + 1` 로 한 바퀴에 집계)
- ④ 틀린 이유 : **두 번 틀림.**
  - set이 중복(동명이인) 정보를 버려서 예제 3에서 빈 집합 → `KeyError`
  - `participant.count(p)` 로 세다가 O(N²) → 10만 명 기준 **추정 124초**. dict 집계로 0.015초
  - 참가자 표를 돌며 "완주자 명단에 있나?" 로 깎으면 같은 이름을 한 번만 깎아 오답 (랜덤 5000회 중 959건 불일치)

### 88 폰켓몬 (2026-08-21)

- ② 실제 정답 방법 : `min(가져갈 수 있는 마리 수, 종류 수)`
- ③ 사용한 자료구조 : set (종류만 필요하고 각 종류가 몇 마리인지는 답에 무관)

## C++ 재구현 — Python → C++ 대응 (2026-08-22~27, LV1 8문제)

Python으로 이미 푼 문제를 C++로 옮기며 얻은 것. **알고리즘이 아니라 언어 차이만** 정리한다.

### 문법·타입

| Python | C++ | 처음 걸린 곳 |
| --- | --- | --- |

| `x[a:b]` (리스트) | `vector<T> v(x.begin()+a, x.begin()+b)` — 끝 제외는 동일 | 52 K번째수 |

### 조용히 틀리는 것들 — 이게 진짜 위험

| 함정 | 증상 | 대응 |
| --- | --- | --- |
| **오버플로** | `int`로 누적하다 21억 넘으면 **음수**가 됨. 에러도 경고도 없음 | 누적·곱셈 결과가 21억 넘으면 `long long` |
| **계산 타입** | `long long`에 담아도 `int * int`는 `int`로 계산돼 이미 망가짐 | **곱하기 전에** 한쪽을 `long long`으로 |
| **`%` 음수** | Python `-3 % 2 == 1`, C++ `-3 % 2 == -1` | 홀짝 판별은 `== 0` / `!= 0` 로 |
| **`/` 음수** | Python `-3 // 2 == -2`(내림), C++ `-3 / 2 == -1`(0쪽 버림) | 음수 나눗셈 나오면 직접 확인 |
| **`//`** | C++에서는 **주석**. `x // 2` 쓰면 뒷부분이 통째로 사라짐 | 정수 나눗셈은 `/` 하나로 충분 |
| **부호 비교** | `size()`(unsigned) `>= k`(int) 에서 k가 음수면 거대한 수로 변환 → `2 >= -1`이 **거짓** | `int n = x.size();` 로 받아두고 비교 |
| **return 누락** | Python은 `None`, C++은 **미정의 동작**. 테스트가 통과해도 운일 뿐 | 마지막에 `throw` 또는 명시적 return |
| **`unordered_map` 순서** | Python dict는 삽입 순서 보장, C++ `unordered_map`은 **순서 없음** | 결과는 원본 목록 순서로 다시 뽑기 |

### 이름 충돌 — `using namespace std;` 의 대가

`std` 의 이름을 지역 변수·함수 이름으로 쓰면 부딪힌다. 실제로 겪은 것:

```
string ref(string s) { ... }
→ error: conversion from 'std::reference_wrapper<...>' to non-scalar type 'std::string'
```

피할 이름: `ref` `count` `max` `min` `size` `data` `begin` `end` `next` `prev` `swap` `distance` `find` `sort` **`stack`** `queue` `array`
→ `cnt`, `expected_of` 처럼 접두·접미를 붙인다.

### 환경·제출

- `sort`는 `<algorithm>`, `runtime_error`는 `<stdexcept>`. **프로그래머스 스켈레톤에는 `<string>`, `<vector>`만 있다.**
  로컬은 통과하는데 프로그래머스에서 `undeclared identifier` 가 뜨면 **거의 항상 include 누락**.
- 프로그래머스는 **clang**, 로컬은 **g++**. 같은 에러를 다르게 표현한다.
- 제출할 때 `#include "../test_runner.h"` 와 `int main()` 은 **빼고** `solution` 함수만 올린다.
- 오타는 C++이 **컴파일 시점에 100% 잡아준다** (`did you mean ...?` 제안까지). 긴 변수명은 타이핑하지 말고 복사.

### 성능 — C++이 항상 빠르지는 않다 (실측)

53번 완주하지 못한 선수, 참가자 100,000명 기준:

| 구현 | 시간 |
| --- | ---: |
| Python | **0.0091s** |
| C++ (프로그래머스 스켈레톤 그대로, 값 복사) | 0.0099s |
| C++ (`const vector<string>&` 참조) | **0.0076s** |

- `vector`를 값으로 받으면 원소를 **전부 복사**한다 (10만 개면 10만 번).
- Python `dict`/`str` 해싱은 C로 짜인 최적화 코드라 해시 위주 문제에서는 C++와 대등하다.
- C++이 크게 이기는 건 **반복 자체가 무거울 때** (83번의 2천만 번 덧셈 등).
- 실전에서는 **스켈레톤 그대로 쓴다.** 시그니처를 고치다 실수하는 비용이 더 크다.
